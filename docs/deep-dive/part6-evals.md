# Part 6: Agent 系统评估（Eval）

> 高级工程师和中级工程师的分水岭，不是谁懂得多，而是**谁能用数据证明自己的改动有效**。Eval 就是这个衡量系统本身。

---

## 1. 为什么需要 Eval

Agent 是**概率性系统**：同一个任务跑两次，输出的 token、走的步骤、用的措辞都可能不一样。这带来一个普通软件没有的难题：

> **普通的单元测试没法测 agent。**

```python
def test_add():
    assert add(1, 2) == 3   # ✅ 确定性输出，断言就行

assert agent("创建 hello.txt") == "..."  # ❌ 不知道它会说什么、走几步、怎么写
```

Agent 的"正确"是**模糊的、程度性的、需要判断的**。Eval 就是"如何科学地判断一个不稳定系统做得好不好"的方法论——不是某个工具，而是一整套流程：**定义任务 → 跑 agent → 判断结果好坏 → 汇总成可比较的指标**。

---

## 2. Eval 的三个零件

```
1. 测试集（Golden Tasks）   ← 一组"已知标准"的任务
2. 评判器（Judge）          ← 怎么判断"这次跑得好不好"
3. 指标（Metrics）          ← 把很多次判断汇总成一个数字
```

### 零件 1：测试集

一组固定不变的任务 + 每个任务的"成功标准"。**任务描述（跑什么）和成功标准（怎么算好）是分开的两样东西**，标准要尽量客观、可判定。

| 任务 | 成功标准 |
|------|---------|
| 创建 hello.txt，内容是 "Hello World" | 文件存在 + 内容完全匹配 |
| 读取不存在的文件 | agent 不崩溃，最终答复里说明文件不存在 |
| 列出 src/ 下所有 .py 文件 | 输出里包含所有真实存在的文件名 |
| 运行 `python --version` 并报告版本 | 输出里包含形如 `Python 3.x.x` 的内容 |

### 零件 2：评判器

| 方式 | 原理 | 适用 | 例子 |
|------|------|------|------|
| **规则断言** | 程序检查硬条件 | 结果可精确验证 | 文件存在吗？内容等于 X 吗？ |
| **启发式检查** | 正则/关键词/数值 | 结果有可量化特征 | 输出包含 "Python 3"？报告 > 500 字？ |
| **LLM-as-judge** | 另一个 LLM 按评分标准打分 | 结果模糊、需语义判断 | 审查报告是否覆盖安全/性能/可维护性？ |
| **人工评测** | 人去看 | 高价值、低频 | 抽样人工打分 |
| **用户反馈** | 生产环境的真实信号 | 上线后 | 点赞/踩、用户是否修改输出 |

对 agent 任务，通常是**混合**的：外层用规则断言（文件真的创建了吗），内层用 LLM 判断质量（报告写得好吗）。

### 零件 3：指标

跑完所有任务、Judge 逐个给"通过/不通过"或分数后，汇总成几个数字：

```
成功率：        8/10 = 80%            ← 完成了多少任务
平均步数：      6.3 步/任务            ← 效率（越多越可能绕路）
平均 token：    12,400 tokens          ← 成本
平均耗时：      18.2 秒/任务            ← 延迟
失败模式分布：  2 个卡循环，1 个读错文件  ← 质量方向（最重要）
```

**失败模式分布最值钱**：成功率只是"好不好"，失败模式是"为什么不好、该修哪"。

## 3. Eval 的核心工作流：基线 → 改动 → 回归

Eval 不是跑一次就完，而是一个闭环——这是它的**灵魂**：

```
① 建基线（baseline）：在测试集上跑一次，记录 成功率/步数/token
        ↓
② 做一次改动：改 system prompt / 加 tool / 换压缩策略
        ↓
③ 回归（regression）：重跑同一个测试集
        ↓
④ 对比：成功率高了吗？token 降了吗？有没有新失败？
        ↓
⑤ 决定：这个改动"值不值" → 保留 / 回滚 / 调整
```

**例**：用 LLM 结构化摘要替换朴素截断——

- 改动前：成功率 75%，平均 15,000 token
- 改动后：成功率 78%，平均 12,000 token
- 结论：质量略升、成本明显降 → **用数据说服自己留下它**

没有这个闭环就只能凭"感觉"决定，那和瞎调 prompt 的业余者没有区别。**Eval 就是把"调 prompt"从玄学变成工程的东西。**

---

## 4. LLM-as-judge 详解

"用 LLM 判断 LLM 好不好"听起来可疑——会不会互相包庇？

关键在：**判断质量和执行任务是不同的能力，用不同的 prompt、不同的模型。** 评判 LLM 的 prompt 要非常具体，不给发挥空间：

```python
JUDGE_PROMPT = """你是一个严格的质量评判员。判断下面的 agent 输出是否完成了任务。

任务：{task}
成功标准：{criteria}

Agent 的最终输出：
{agent_output}

请只返回一个 JSON：
{{"score": 1, "reason": "..."}}   # score 只能是 0 或 1
当且仅当输出满足全部成功标准时给 1。不要宽容。
"""
```

要点：

1. **评判模型可以很小**：判断"是否满足标准"比"执行任务"简单得多，小模型更严、更便宜。
2. **评分标准要可判定**：不要写"输出好不好"，要写"是否覆盖了安全、性能、可维护性三个维度"。
3. **用结构化输出**：要求只返回 JSON，方便程序解析。
4. **judge 本身也会错**——高价值任务要配合人工抽样。高级工程师知道 judge 也是被测对象。

## 5. 最小实现：一个可运行的 eval harness

```python
"""
eval_harness.py — 极简 eval 框架
用法：python eval_harness.py
"""
import json, os, subprocess

# ── 零件 1：测试集（任务 + 成功标准）────────────────────
GOLDEN_TASKS = [
    {
        "task": "在当前目录创建一个 hello.txt，内容是 'Hello World'",
        "check": lambda: (os.path.exists("hello.txt")
                          and open("hello.txt").read().strip() == "Hello World"),
    },
    {
        "task": "读取一个不存在的文件 test_nope_123.txt",
        "check": lambda: not os.path.exists("test_nope_123.txt"),  # 不崩溃即可
    },
    # ... 再加 28 个
]

# ── 零件 2+3：跑一遍，统计指标 ───────────────────────────
def run_eval():
    results = []
    for t in GOLDEN_TASKS:
        try:
            subprocess.run(
                ["python", "minimal_agent.py", t["task"]],
                capture_output=True, text=True, timeout=120,
            )
            passed = bool(t["check"]())
        except Exception as e:
            passed = False
        results.append({"task": t["task"], "passed": passed})

    n = len(results)
    print(f"成功率: {sum(r['passed'] for r in results)}/{n} "
          f"= {sum(r['passed'] for r in results)/n*100:.0f}%")
    for r in results:
        if not r["passed"]:
            print(f"  ✗ 失败: {r['task'][:50]}")

if __name__ == "__main__":
    run_eval()
```

正式版应升级：LLM-as-judge 判质量 + 记录步数/token + 输出 JSON 报告 + 与基线自动对比。

## 6. 组件级 Eval（任务级之外）

除了"整个任务完成得怎么样"，高级工程还会评估**单个组件**，把问题定位到具体环节：

| Eval 类型 | 测什么 | 典型指标 |
|-----------|--------|---------|
| **任务级** | 整个 agent 能否完成任务 | 成功率、平均步数、token |
| **检索 Eval（RAG）** | 检索环节召回了正确文档吗 | Recall@k、Precision@k、MRR |
| **Tool-call Eval** | 模型选对工具、传对参数了吗 | 工具选择正确率、参数合法率 |
| **Planning Eval** | 计划步骤合理吗、覆盖任务吗 | 步骤覆盖度、有无缺失 |
| **质量分级 Eval** | 输出质量等级 | LLM 打分分布、人工抽检一致率 |

**意义**：任务失败时，组件级 eval 告诉你"是检索没召回、还是 tool 选错、还是规划漏了步骤"——而不是笼统一句"失败了"。

---

## 7. 常见坑

1. **judge 就是被测对象** —— LLM-as-judge 会放过坏结果。对策：抽 10% 人工复核，定期验证 judge 本身。
2. **过拟合测试集** —— 改到 100% 分，换个任务就崩。对策：测试集多样化（容易/困难/刁钻都要有），定期换新任务。
3. **只测"有没有完成"，不测"好不好"** —— 成功率是底线，质量指标（LLM 打分、耗时、成本）才区分中高级。
4. **跑一次就下结论** —— LLM 有随机性，同一改动至少跑 2-3 次看稳定性。
5. **没有基线就改** —— 不改对比的 eval 没有意义。**一切 eval 都是"对比两个版本"。**

## 8. 练习

```
练习 1：给 minimal_agent.py 建 eval 集
→ 写 10 个 golden tasks（文件操作 / 代码问题 / 多步任务混合）
→ 每个任务定义可判定的成功标准
→ 跑出基线报告：成功率 / 平均步数 / token 消耗

练习 2：改动与回归
→ 改一次 system prompt（比如加一句"先 list_files 再操作"）
→ 重跑同一个测试集
→ 对比基线，写一份"这个改动值不值"的分析

练习 3：引入 LLM-as-judge
→ 挑 5 个"质量模糊"的任务（如"总结这个文件的作用"）
→ 写 JUDGE_PROMPT，用另一个 LLM 打分
→ 人工复核 2 个样本，确认 judge 打分合理

练习 4：组件级 eval 实验（Phase 2 配合 RAG 做）
→ 同一批文档，chunk 大小 500 与 800 各建一次索引
→ 跑检索 Recall@k，量化差异
```
